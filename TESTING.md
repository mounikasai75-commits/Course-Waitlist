# Test coverage map

Every test uses its own isolated SQLite in-memory database (a private open `:memory:` connection per test via `TestDatabase`, or a separate `WebApplicationFactory` host per API test). No test depends on execution order. No database behavior is mocked or replaced by the EF InMemory provider. Tests assert the final database/queue state, not only response messages.

Run: `dotnet test CourseWaitlist.sln` (128 tests).

Files: `EnrollmentServiceTests` (E), `DropServiceTests` (D), `ConcurrencyTests` (C), `CourseEndpointTests` (A), `AcceptanceGapTests` (G: `EnrollTimePromotionEligibilityTests`, `CourseApiAcceptanceTests`), `PersistenceTests` (P), `WaitlistOrderingTests` (O).

## Known gaps

- Eligibility is flipped directly in the database in tests; there is no API to change it (by design). Those tests run it only while no request is in flight.
- Concurrency tests repeat contended scenarios but cannot prove the absence of races; the guarantee is single-process only (see DESIGN.md).
- The prerequisite representation, re-enrollment-after-drop behavior, HTTP status mapping, enroll-time promotion, and single-process scope are confirmed by the developer; tests encode these choices.
